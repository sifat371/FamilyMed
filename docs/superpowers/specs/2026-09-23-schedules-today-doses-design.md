# FamilyMed V1 — Schedules, Doses, Today, and Reminder Design

Date: 2026-09-23
Branch: `feat/schedules-today-doses`
Status: Design for review

## 1. Purpose

This slice turns a FamilyMed medication record into an actionable daily care routine. A caregiver should be able to set reminder times for a family member's medication, see today's scheduled doses, mark what happened, snooze a pending dose, and review the resulting history.

The product remains a medication-care tool, not a prescribing system. FamilyMed never claims that a marked dose was independently verified as swallowed. The UI must describe `taken` as family/user-confirmed status.

The target golden path is:

`Add medication → set routine → enable reminders or choose Not now → generate doses → Today → mark taken / snooze / skip → history`

## 2. Existing Context

The current `main` branch already provides:

- FastAPI + PostgreSQL with authenticated user sessions.
- Family ownership/membership scoping.
- Family member profiles with IANA timezone values.
- `MemberMedication` records with `draft`, dates, free-text name/strength/form, and server-side ownership checks.
- Flutter authentication, secure token storage, routing, family member screens, and manual medication entry.
- Riverpod, Dio, Drift, localization, and the FamilyMed theme.

This slice extends those patterns. It does not create a parallel auth, repository, or state-management architecture.

## 3. Scope

### In scope

- One canonical active/paused medication schedule per member medication.
- One or more local reminder times per schedule.
- Optional source instruction text and meal relation retained separately from reminder clock times.
- Durable scheduled-dose rows generated by the backend.
- A rolling 30-day future dose window.
- Dose reconciliation from `upcoming` to `pending` and eventually `missed`.
- Today dashboard grouped by family member.
- Mark Taken, Snooze, Skip, and history correction.
- Append-only dose event logs.
- Medication pause, resume, natural completion, and manual end behavior.
- Per-user/per-member notification preference with a 15-minute default snooze.
- Local Android notifications.
- Offline Today cache and offline queueing for dose actions.
- Member medication history with a clearly named `marked_adherence_percentage`.
- English/Bangla localization for all new user-visible strings.

### Out of scope

- Prescription OCR/HTR and AI-derived schedule creation.
- Drug interactions, diagnosis, dose recommendations, or medical advice.
- Multiple caregivers editing the same family simultaneously beyond existing membership rules.
- Caregiver escalation when a dose is not marked.
- Pharmacy ordering/refills.
- Doctor or hospital portals.
- A production background worker/cron service.
- Full four-tab `Today | Family | History | Me` shell redesign. This slice introduces Today as the authenticated home and keeps History accessible from the relevant family member. A broader navigation polish pass can follow.
- Offline creation or editing of schedules. Routine setup requires the API; Today viewing and dose actions are the offline-supported paths in this slice.

## 4. Product and Safety Rules

1. Prescription/source instruction and reminder time are different data.
2. The routine screen must state: **“Reminder times are not part of the prescription.”**
3. `taken` means **marked taken by a family/user**, not verified ingestion.
4. Snooze never becomes a dose status. The dose remains `pending` with `snoozed_until`.
5. Notification permission does not control whether the medication or schedule is active. Choosing “Not now” or denying permission leaves the routine active and Today functional.
6. Schedule edits never rewrite historical dose events.
7. Cross-family resource access must return the same not-found behavior used by the current ownership layer so resource existence is not leaked.
8. Client retries must not duplicate dose actions or dose logs.

## 5. Chosen Architecture

The backend owns the canonical schedule and durable dose ledger. Flutter caches the Today projection and queues dose actions when offline.

```text
MemberMedication
      ↓
MedicationSchedule
      ↓
ScheduleTime(s)
      ↓
30-day rolling generator
      ↓
ScheduledDose(s)
      ↓
Taken / Snooze / Skip / Missed / Correct
      ↓
DoseLog (append-only)
```

This is preferred over computing doses dynamically at read time because historical expectations must remain stable when a schedule changes. It is preferred over phone-owned dose generation because the backend must remain the source of truth across devices and future caregivers.

No new background-worker service is required in this slice. A shared reconciliation service is called by schedule mutations, Today/history reads, and dose actions to keep the rolling window and due-state transitions current. The design intentionally allows the same service to be called later by a real scheduler/worker without changing domain semantics.

## 6. Domain Model

### 6.1 `medication_schedules`

Fields:

- `id` UUID primary key.
- `member_medication_id` FK → `member_medications.id`.
- `raw_instruction` nullable text. Example: `1+0+1 PC`.
- `meal_relation` nullable string enum: `before_food`, `after_food`, `with_food`, `none`, `unspecified`.
- `timezone` IANA timezone string. Defaults from the family member when created.
- `start_date` local calendar date.
- `end_date` nullable local calendar date.
- `status`: `active`, `paused`, or `ended`.
- `created_by_user_id` FK → `users.id`.
- standard timestamps.

V1 invariant: a member medication may have at most one schedule whose status is `active` or `paused`. Old `ended` schedules may remain for audit/history.

Creating the first schedule for a `draft` medication changes the medication to `active` in the same transaction.

### 6.2 `schedule_times`

Fields:

- `id` UUID primary key.
- `schedule_id` FK → `medication_schedules.id`.
- `period`: `morning`, `afternoon`, `evening`, `night`, or `custom`.
- `local_time` wall-clock time.
- `quantity` decimal, not floating point.
- `unit` short free text, e.g. `tablet`, `capsule`, `mL`.
- `sort_order` integer.

Rules:

- At least one and at most eight times per schedule.
- Times must be unique within one schedule.
- `quantity > 0`.
- `unit` must be nonblank after trimming.

### 6.3 `scheduled_doses`

Each row is a durable occurrence and contains snapshots needed for stable history.

Fields:

- `id` UUID primary key.
- `schedule_id` FK.
- `schedule_time_id` nullable FK; `ON DELETE SET NULL` so historical rows survive schedule-time replacement.
- `family_member_id` FK.
- `member_medication_id` FK.
- `scheduled_at` timezone-aware UTC timestamp.
- `scheduled_local_date` date snapshot.
- `scheduled_local_time` time snapshot.
- `timezone` timezone snapshot.
- `quantity` decimal snapshot.
- `unit` string snapshot.
- `meal_relation` nullable snapshot.
- `status`: `upcoming`, `pending`, `taken`, `skipped`, or `missed`.
- `snoozed_until` nullable UTC timestamp.
- `taken_at`, `skipped_at`, `missed_at` nullable UTC timestamps.
- standard timestamps.

A unique constraint prevents duplicate occurrences for the same schedule/local date/local time.

The row's current `status` is a convenient projection. `dose_logs` is the audit trail.

### 6.4 `dose_logs`

Append-only event table:

- `id` UUID primary key.
- `scheduled_dose_id` FK.
- `action`: `created`, `became_pending`, `snoozed`, `marked_taken`, `skipped`, `missed`, `corrected`.
- `performed_by_user_id` nullable FK. System events such as generation/missed transitions use null.
- `client_action_id` nullable UUID.
- `occurred_at` UTC timestamp representing when the event happened from the user's/system's perspective.
- `recorded_at` server timestamp.
- `metadata` JSONB.

`client_action_id` is unique when non-null. The mobile app generates it once for each user action and reuses it for retries. This is the idempotency key for offline replay.

Existing log rows are never edited or deleted through application APIs.

### 6.5 `notification_preferences`

Fields:

- `id` UUID primary key.
- `family_member_id` FK.
- `user_id` FK.
- `enabled` boolean, default false.
- `default_snooze_minutes` integer, default 15.
- `caregiver_escalation_enabled` boolean, fixed/default false in V1.
- standard timestamps.

Unique on `(user_id, family_member_id)`.

No escalation behavior is implemented in this slice.

## 7. Time Semantics

### 7.1 Source of time

- Schedule input is a local date/time plus an IANA timezone.
- Generated `scheduled_at` values are stored in UTC.
- Today/history grouping uses the dose's stored local date/time snapshots.
- The initial Bangladesh launch path is tested against `Asia/Dhaka`.

General DST-specific UI behavior is not a launch requirement for this Bangladesh-first slice. The implementation must still reject invalid timezone identifiers rather than silently falling back to UTC.

### 7.2 Rolling generation

For an active schedule, the backend ensures occurrences exist from the member's current local date through local date + 29 days, bounded by schedule/medication start and end dates.

Generation is idempotent. Calling it repeatedly must not create duplicate dose rows or duplicate `created` logs.

The reconciliation service runs before:

- returning `/today`;
- returning history;
- processing a dose action;
- after schedule create/update/resume;
- after medication lifecycle actions.

A later background worker may call the same service, but is not needed for V1 correctness when the app is in use.

### 7.3 Status transitions

`upcoming → pending` when `scheduled_at <= now` and the dose is not final.

A pending dose becomes `missed` only after its member-local calendar day has ended. If it has been snoozed past that boundary, the missed threshold is the later of local-day end and `snoozed_until`.

`pending` and `upcoming` are non-final. `taken`, `skipped`, and `missed` are final for ordinary actions but can be changed through the explicit correction path described below.

### 7.4 Snooze

Snooze is allowed only for a `pending` dose.

The body supplies a `client_action_id` and `snoozed_until`. `snoozed_until` must be later than the action's `occurred_at`.

The dose remains:

```text
status = pending
snoozed_until = <new UTC time>
```

Repeated snoozes are allowed and each creates a separate append-only event, provided each uses a distinct `client_action_id`.

## 8. Schedule Mutation Semantics

### 8.1 Create

- Requires writable access to the medication's family member.
- Rejects an `ended` medication.
- Rejects creation if an active/paused schedule already exists.
- Creates schedule and times transactionally.
- Activates a `draft` medication.
- Generates the rolling window.

### 8.2 Edit

Editing a schedule may change instruction text, meal relation, dates, timezone, and times.

The cutoff is server `now`:

- Taken/skipped/missed doses are never modified.
- Pending doses whose scheduled time has already arrived are never silently moved.
- Only future `upcoming` doses with `scheduled_at > now` are removed and regenerated from the new schedule.

This preserves what the family already saw or acted on.

### 8.3 Pause

Pausing a medication:

- changes medication to `paused`;
- changes its active schedule to `paused`;
- preserves all historical/final and already-pending doses;
- removes future `upcoming` doses after server `now`;
- schedules no new notifications for removed doses.

### 8.4 Resume

Resuming:

- returns medication and its schedule to `active`;
- ensures the next 30-day window from the member's current local date;
- does not recreate past occurrences that were intentionally absent during the pause.

The resume date acts as a new lower bound for generation even if the original schedule start date is earlier.

### 8.5 Manual end

Ending a medication:

- sets medication `ended` and schedule `ended`;
- removes future `upcoming` doses;
- preserves pending and historical doses;
- cancels matching future local notifications on the device after sync.

### 8.6 Natural completion

If a medication/schedule has an `end_date`, reconciliation changes the medication to `completed` and schedule to `ended` only after that local date has fully elapsed and there are no non-final doses for that date or earlier.

## 9. Dose Actions and Corrections

### 9.1 Mark taken

Allowed from `upcoming` or `pending` when the caregiver confirms the dose has actually been taken. Early marking is allowed because the app should record what the family says happened rather than force the reminder clock to be the clinical truth.

The request contains:

- `client_action_id` UUID;
- `occurred_at` UTC timestamp.

The backend sets status `taken`, sets `taken_at=occurred_at`, clears `snoozed_until`, and appends `marked_taken`.

### 9.2 Skip

Allowed from `upcoming` or `pending`. It sets `skipped`, records `skipped_at`, clears snooze, and appends `skipped`.

### 9.3 Ordinary action conflicts

Ordinary Taken/Skip/Snooze actions against a different final state return `409 DOSE_ALREADY_FINALIZED` with the current dose projection.

Repeating the same user action with the same `client_action_id` returns success with the current dose and does not append another log.

### 9.4 Correct history

A separate correction endpoint allows a caregiver to correct a final dose to `taken`, `skipped`, or `missed`. This exists so an automatically missed dose can later be accurately marked taken.

A correction:

- requires writable family access;
- requires a new `client_action_id`;
- updates the current status projection;
- retains prior timestamps/logs;
- sets the timestamp associated with the corrected status;
- appends a `corrected` event containing previous status, new status, and optional reason.

The UI labels this as correcting the record, not deleting history.

## 10. API Surface

All endpoints use the existing bearer auth/error-envelope conventions.

### Schedules

```text
POST  /api/v1/member-medications/{medication_id}/schedules
GET   /api/v1/member-medications/{medication_id}/schedule
PATCH /api/v1/schedules/{schedule_id}
```

Schedule create/update payload includes:

- `raw_instruction` nullable;
- `meal_relation`;
- `timezone`;
- `start_date` / optional `end_date`;
- `times[]` with `period`, `local_time`, `quantity`, `unit`.

### Medication lifecycle

```text
POST /api/v1/member-medications/{medication_id}/pause
POST /api/v1/member-medications/{medication_id}/resume
POST /api/v1/member-medications/{medication_id}/end
```

### Today

```text
GET /api/v1/today
```

Today returns every accessible family member with doses for that member's current local date. Each member payload includes:

- member identity;
- local date/timezone;
- `taken_count`;
- `total_count` for all scheduled doses that local day;
- ordered dose projections.

Dose projection includes medication name/strength, quantity/unit, meal relation, scheduled time, effective reminder time, status, and snooze information.

### Dose actions

```text
POST /api/v1/doses/{dose_id}/taken
POST /api/v1/doses/{dose_id}/snooze
POST /api/v1/doses/{dose_id}/skip
POST /api/v1/doses/{dose_id}/correct
```

### History

```text
GET /api/v1/family-members/{member_id}/history?from=YYYY-MM-DD&to=YYYY-MM-DD
```

Default range is the most recent 30 local calendar days; maximum requested range is 90 days.

History groups by local date and exposes the immutable event history needed for correction/audit.

`marked_adherence_percentage` is explicitly defined as:

```text
100 × taken_current_status / (taken + skipped + missed current statuses)
```

Upcoming/pending doses are excluded. If the denominator is zero, the field is null. The UI must call this “marked adherence,” never verified adherence.

### Notification preference

```text
GET   /api/v1/family-members/{member_id}/notification-preference
PATCH /api/v1/family-members/{member_id}/notification-preference
```

V1 mutable fields are `enabled` and `default_snooze_minutes`. Escalation remains false/unavailable.

## 11. Flutter Experience

### 11.1 Routine setup

From a medication card/profile, an active **Set routine** action opens a routine form.

Example:

```text
Metformin 500 mg
Prescription / source instruction: 1 + 0 + 1 • after food

Morning     8:00 AM     1 tablet
Night       8:00 PM     1 tablet

Reminder times are not part of the prescription.
```

Required:

- at least one reminder time;
- unique times;
- positive quantity;
- nonblank unit;
- valid date range.

Submitting requires network access. If creation fails, entered values remain intact.

### 11.2 Enable reminders

After schedule creation, show the existing golden-path concept:

```text
Enable reminders
[ Enable reminders ]
[ Not now ]
```

Choosing Enable requests OS notification permission where required and updates the backend preference only when enabled. Permission denial shows a calm explanatory state; it does not disable the routine.

Choosing Not now stores/keeps preference disabled and continues to Today.

### 11.3 Today as authenticated home

After a user has family members, successful login returns to `/today`. A restored authenticated session also uses `/today` as the default home. Registration still routes a user with no members through the existing care-for onboarding.

The full four-tab navigation shell is not part of this slice.

Today example:

```text
Amma
2 / 3 marked taken

✓ 8:00 AM  Metformin 500 mg
✓ 8:00 AM  Amlodipine 5 mg
○ 8:00 PM  Metformin 500 mg
```

Status is communicated by icon + text, never color alone.

If the API is unavailable but cached Today data exists, the screen renders the cache with an offline indicator.

### 11.4 Dose action screen

```text
Amma's evening dose

Metformin 500 mg
1 tablet • After food
Scheduled 8:00 PM

[ Mark as taken ]
[ Snooze 15 min ]
[ Skip this dose ]

Taken status is based on family/user confirmation.
```

Taken and Skip use immediate optimistic local updates. Snooze keeps the dose pending and changes the effective reminder time.

### 11.5 History

The member profile gains a History action/list. History shows scheduled time, current status, action time, and corrections when present. A final dose can open **Correct record**, which uses the explicit correction API.

## 12. Local Notifications

Use a notification scheduler abstraction in Flutter so behavior is testable without the platform plugin.

Production implementation uses local notifications. Notifications are scheduled only for non-final cached doses when preference is enabled.

Rules:

- Notification identity is deterministic from dose ID so rescheduling replaces instead of duplicates.
- Finalizing a dose cancels its pending notification.
- Snoozing cancels/replaces the existing notification for `snoozed_until`.
- Schedule edits, pause, end, and Today refresh reconcile the local scheduled notification set against server/cached dose IDs.
- Tapping a notification deep-links to the dose action screen.
- Android notification permission is requested only in response to the user's Enable Reminders action.
- Exact-alarm privileges are not required by this slice; the implementation uses the platform/plugin mode that does not require restricted exact-alarm permission. The UI must not promise second-level exact delivery.

## 13. Offline Cache and Action Queue

Schedule creation/editing remains online-only. Today viewing and dose actions are offline-capable.

Drift schema is bumped and gains at least:

### `cached_doses`

A local Today/history projection containing the identifiers and display/status fields required to render the dose without network access.

### `sync_operations`

Fields include:

- local UUID / `client_action_id`;
- dose ID;
- action (`taken`, `skip`, `snooze`, `correct`);
- JSON payload;
- created timestamp;
- attempt count;
- last error nullable.

Action flow:

```text
User action
   ↓
optimistic cached-dose update
   ↓
insert sync operation with stable client_action_id
   ↓
try API immediately
   ↓
if success: replace local projection with server response + delete op
if network failure: keep op
```

Queue draining is opportunistic in V1:

- app startup/session restore;
- app resume;
- after a successful API interaction;
- immediately after creating an operation.

No `connectivity_plus` dependency is required merely to observe network state.

Conflict handling:

- `401`: existing `ApiClient` refresh behavior applies.
- duplicate `client_action_id`: backend returns idempotent success.
- `409 DOSE_ALREADY_FINALIZED`: refetch/use the server's current dose, remove the local op, and show a non-destructive message that the record changed elsewhere.
- `404`: discard the stale cache entry after server confirmation and remove the op.
- other server errors: retain the op for retry unless the error is a permanent validation error; show the user that sync is pending/failed rather than silently losing the action.

## 14. Error Handling and Validation

Use the current API error envelope and Flutter form-error patterns.

Important errors:

- `ACTIVE_SCHEDULE_EXISTS` — 409.
- `INVALID_TIMEZONE` — 422.
- `INVALID_SCHEDULE` — 422.
- `DOSE_ALREADY_FINALIZED` — 409.
- `DOSE_NOT_PENDING` — 409 for snooze on non-pending dose.
- `RESOURCE_NOT_FOUND` — 404 for inaccessible or nonexistent family-owned resources.

Duplicate submissions are blocked in Flutter while a schedule/action request is in flight, while backend idempotency protects retries.

## 15. Service Boundaries

Backend modules should remain focused:

```text
app/schedules/
  models.py
  schemas.py
  repository.py
  service.py
  generation.py
  router.py

app/doses/
  schemas.py
  repository.py
  service.py
  reconciliation.py
  router.py

app/notifications/
  models.py
  schemas.py
  service.py
  router.py
```

`generation.py` owns deterministic occurrence creation. `reconciliation.py` owns time-derived state transitions. Routers do not contain scheduling logic.

Flutter uses feature-first boundaries:

```text
features/schedules/
features/today/
features/doses/
features/history/
core/notifications/
core/sync/
```

Platform notification code is hidden behind an interface. Offline queue code does not know widget/navigation details.

## 17. Success Criteria

This slice succeeds when a FamilyMed caregiver can reliably convert a medication into a daily routine, see the family member's actual scheduled-dose ledger, record what happened even during temporary network loss, receive local reminders when enabled, and later understand/correct the marked history without FamilyMed making a clinical claim it cannot verify.
